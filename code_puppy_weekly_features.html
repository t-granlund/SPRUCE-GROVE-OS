Unified Session Store & Headless Save-Back

Feature June 26 PR #507
📁

One Directory, Everything

Named sessions (/dump_context) and auto-saves (autosaves/) now live in the same canonical directory. No more hunting across two locations for your sessions.

🔖

Named Sessions in the Menu

The /resume picker now shows a Named sessions section above auto-saves, sorted by most recently modified — your named work is always first.

⚡

Headless Save-Back: -r NAME -p "…"

Run a one-shot prompt on a named session from the command line, and the completed turn is automatically written back. No more lost headless work.

🚚

Auto-Migration from Legacy

Any files you had stashed in the old contexts/ directory are moved to autosaves/ automatically on first launch — one-time, atomic, and safe to interrupt.

How to use it:
  • Interactive: Just use /resume as before — your named sessions now appear at the top.
  • Headless one-shot: code-puppy -r my-project -p "summarize the last changes" — the answer is saved back into my-project.pkl automatically.
  • Lazy-create: If my-project doesn't exist yet, it's created for you. Session names must be 1–128 chars of [A-Za-z0-9._-].
  • Protection: The auto_session_ prefix is reserved for system-generated saves — user input using that prefix is rejected to prevent collisions.

Press / to Search Sessions by Content

Feature June 25 PR #500
⌨️

Press / to Filter

Inside /resume, pressing / enters search mode. Type anything — it matches against the actual content of each session (what was said), not just the filename or timestamp.

🚀

Pre-warmed Index

Sessions are indexed in the background as soon as the picker opens, so your first search is nearly instant. An Indexing N/M… indicator shows progress while it loads.

🔒

Thread-Safe & Non-blocking

Filtering runs on a worker thread so the UI stays responsive. A cache protects broken session files from being re-read on every keystroke — errors are tolerated silently.

How it works: A lazy-cached SessionContentIndex extracts the raw text of every message in each session pickle. Cheap checks (session name, timestamp, message count) short-circuit before touching the file — so if the needle matches the filename, it's instant. Search is case-insensitive. Press Enter to select, Esc to cancel back to the full list.

/undo Command

Feature June 25 PR #502
🔁

Undo File Modifications

Type /undo to reverse the last file change Code Puppy made during a session. Every file write is tracked by the UndoManager automatically — no configuration needed.

🪝

Hooked into File Ops

File modification hooks are wired directly into the UndoManager, so any write Code Puppy performs — edits, creates, overwrites — is undo-able without you having to think about it.

This is one of the most-requested quality-of-life features: when an agent modifies a file in a way you didn't intend, you no longer need to git checkout or manually revert. Just type /undo and the previous state is restored.
📋

/plan Command — Planning-Only Mode

Feature June 25 PR #503
What it does: The new /plan slash command puts Code Puppy into a planning-only mode — the agent reasons through what it would do, but does not execute any tool calls or write any files.

Why it's useful:
  • Preview the agent's intended actions before committing to them.
  • Catch mistakes in the plan before any files are touched.
  • Use it in code reviews or dry-runs: "If I asked you to refactor this module, what would you do?"
  • Pairs with /undo for a safer iterative workflow: plan → approve → execute → undo if wrong.

Per-plugin Contribution View

📍

POSIX Path Display

Plugin file paths are now shown in POSIX format regardless of platform, so paths look consistent and copyable everywhere — no more Windows backslash confusion.

Plugin CLI Argument Hooks

Feature June 29 PR #512
🧲

register_cli_args Hook

Plugins can now add their own top-level command-line flags to the code-puppy CLI — without touching core code. The hook fires with the live ArgumentParser before parse_args().

⚙️

handle_cli_args Hook

After parsing, plugins inspect the result and can short-circuit startup entirely — returning {"handled": True, "exit_code": 0} terminates cleanly with the plugin's own exit code.

🚪

Proper Exit Code Propagation

Plugin exit codes now reach the OS process exit status via sys.exit(rc). Shell scripts and CI pipelines can finally rely on code-puppy's exit status when plugins are involved.

Example — adding a plugin flag:
# my_plugin/register_callbacks.py from code_puppy.callbacks import register_callback def _register_args(parser): parser.add_argument( "--myplugin-export", action="store_true", help="Export results instead of printing", ) def _handle_args(args): if args.myplugin_export: do_export() return {"handled": True, "exit_code": 0} return None # let normal startup proceed register_callback("register_cli_args", _register_args) register_callback("handle_cli_args", _handle_args)

Convention: prefix your flags with your plugin name (e.g. --myplugin-foo) to avoid argparse collisions with other plugins or core flags.

MCP Tool Argument Coercion

Fix June 29 PR #506
The problem: MCP tool calls that required arrays, booleans, or numbers always failed with errors like "string found, array expected" or "expected boolean, received string." This affected multiple MCP servers (SonarQube, Supabase, and others).

Root cause: The model layer emits complex values as JSON strings (e.g. "[\"public\"]", "false", "100"). The pydantic-ai layer that code-puppy delegates to performs zero coercion against each tool's real schema, so the downstream server rejected them.

The fix: A new tool_arg_coercion module intercepts every MCP tool call and coerces stringified values back to their correct types before forwarding — driven by the tool's own JSON Schema. It handles:
  • Arrays & objects — parsed via json.loads()
  • Booleans — "true"/"false" (case-insensitive)
  • Integers & floats — including "100.0" → 100
  • Union types — handles anyOf/oneOf schema shapes
  • Passthrough — anything it can't confidently coerce is left untouched
This applies uniformly to all MCP servers with no per-server configuration needed.
🔄

Streaming Error Recovery & Diagnostics

Fix June 29 PR #513
🌊

Catches Wrapped Errors

pydantic-ai 1.56 wraps raw connection errors in ModelAPIError/ModelHTTPError. The retry classifier now walks the full exception chain (depth-capped, cycle-safe) to catch these, so real network blips auto-retry instead of surfacing a 60-line traceback.

📝

Error Log at ~/.code_puppy/logs/errors.log

Every retry attempt, exhaustion event, and friendly error render is now written to an on-disk log. The UI stays calm; SRE/support gets a full audit trail. Each entry has a distinctive context string per call site.

Gateway errors now auto-retried: DNS hiccups · upstream_idle_timeout · upstream_stream_error · error decoding response body · peer-closed socket.

Log entry contexts:
  • streaming_retry: transient exception on attempt N/M
  • streaming_retry: exhausted all M attempts — giving up and re-raising
  • cli_runner._render_turn_exception: transient model/connection error …
  • cli_runner._render_turn_exception: non-transient turn exception …
Validated against 11,049 unit tests + live headless testing that captured 12 per-attempt and 4 exhaustion log entries from real gateway blips.
👥

Sub-agent Panel: Rows Now Clear Correctly

Fix June 29 PR #509
The problem: The live running-agents panel could leave sub-agent rows frozen on "thinking…" indefinitely. Completed sibling agents accumulated visible rows even after finishing, while a parent kept running.

Root cause: state.mark_done() was only called when SubAgentResponseMessage reached the renderer — but in high-output mode, that emit is suppressed when tokens have already streamed inline. With no fallback, parent agents waiting on children stayed on their last status forever.

The fix: _on_post_tool_call now treats the invoke_agent / invoke_agent_with_model tool return as the authoritative completion signal (success or failure), independent of whether SubAgentResponseMessage was emitted. Rows now correctly show "completed" instead of lying about "thinking…".
🗄️

Concurrent Multiprocess Kennel Writes Fixed

Fix June 30 PR #515
The problem: Under concurrent multiprocess load, the Puppy Kennel (the SQLite-backed session storage backend) was silently dropping writes — all 500 writes in a stress test returned count_drawers == 0.

Two root causes fixed:
  • Environment isolation: is_enabled() was ignoring spawn process boundaries — spawned children re-read the developer's real puppy.cfg, so a local kennel_enabled = false silently no-op'd every child write. A new PUPPY_KENNEL_ENABLED environment variable (inherited across spawn) overrides the config file in child processes.
  • WAL ordering: PRAGMA busy_timeout was applied after journal_mode=WAL, so the first concurrent initialize() could hit "database is locked" before the busy handler was armed. Reordered to arm busy_timeout first.
These fixes ensure all parallel writes land reliably in the Kennel under real multiprocess load.
